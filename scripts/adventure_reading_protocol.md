# 어드벤처 지도 판독 규약

지도 이미지 1장에서 **총 칸 수 · ? 행운카드 위치 · 포탈 위치와 이동칸수**를 뽑는 절차.
지도 1~25번을 이 절차로 판독했고 전부 검증식을 통과했다. 같은 결과가 나오도록 그대로 따를 것.

---

## 0. 왜 이 규약이 필요한가

게임 화면에는 배경(덩굴·석벽·나무·NPC·캐릭터)이 잔뜩 깔려 있어서 원본만 보면
칸 경계와 경로 방향을 자주 틀린다. 그래서 **배경을 걷어낸 흑백 뷰**와
**검출된 칸 좌표 목록**을 먼저 만들고, 마지막에 **검증식으로 자기 채점**한다.

---

## 1. 준비 — 뷰와 좌표 생성

```bash
cd D:/git/Latale-Combat-Power-Calculator
ADV_OUT=<출력디렉터리> PYTHONIOENCODING=utf-8 python - <<'PYEOF'
import sys
sys.path.insert(0,'scripts')
from adventure_extract import *
from adventure_overlay import mask_view
tpl = load_templates()
for st in [26, 27]:                      # ← 담당 지도 번호
    im, tiles, _ = analyze(f'public/assets/adventure/map-{st:02d}.webp', verbose=False)
    mask_view(st)                        # mk<NN>.png = 흑백 윤곽선 뷰
    rows = {}
    for t in tiles:
        rows.setdefault(round(t['cy']/50), []).append(int(t['cx']))
    print(f'--- map-{st:02d}  칸후보 {len(tiles)}')
    for k in sorted(rows):
        print(f'   y~{k*50:4d}: {sorted(rows[k])}')
    print('   ?  ', [(int(b['cx']), int(b['cy'])) for b in find_qcards(im)])
    print('   OUT', [(int(b['cx']), int(b['cy'])) for b in find_outs(im)])
    print('   NXT', [(int(b['cx']), int(b['cy'])) for b in find_next(im)])
    print('   +N ', [(v['value'], int(v['cx']), int(v['cy']))
                     for v in classify_digits(group_numbers(find_digit_glyphs(im)), tpl)])
PYEOF
```

생성물과 용도:

| 자료 | 용도 | 신뢰도 |
|---|---|---|
| `mk<NN>.png` 흑백 윤곽선 뷰 | 경로가 어디서 꺾이고 어디서 끊기는지 **구조 판단** | 높음 (배경 제거됨) |
| `y~NNN:` 칸 좌표 목록 | 각 행/열에 칸이 몇 개인지 | 중간 (오검출·누락 있음) |
| `?` / `OUT` / `+N` 좌표 | 칸 내용과 이동칸수 | 높음 (`+N` 숫자는 거의 정확) |
| 원본 `map-NN.webp` | 위 자료로 애매할 때 최종 확인 | 최고 (단 배경 잡음) |

**흑백 뷰가 하얗게 비거나 노이즈투성이면**(수풀·석벽 배경) 원본 이미지를 직접 읽어라.
map-08 은 아예 흰 윤곽선이 없는 지도였고, map-12 는 수풀 때문에 흑백 뷰가 무용지물이었다.

## 2. 경로 추적

칸들은 **분기 없는 한 줄 사슬**이다. 시작칸부터 NEXT칸까지 순서대로 1, 2, 3… 번호를 매긴다.

- **시작칸**: 보통 좌하단. 흰 화살표 배지(◁)가 붙어 있거나 캐릭터가 서 있다.
  화살표 배지는 칸 *위/옆*에 그려지므로, 배지 바로 옆 칸이 1번이다.
- **끝칸**: `NEXT` 표지판이 있는 칸. 파란 깃발이 옆에 꽂혀 있는 경우가 많다.
  NEXT 가 안 보이면 사슬의 반대쪽 끝이 마지막 칸이다.
- 지도마다 구조가 다르다: 가로 행 뱀 모양(map-01), 세로 기둥 뱀 모양(map-02·11·21·23·24),
  계단식(map-07), 혼합형 등. **흑백 뷰의 실루엣을 보고 판단**할 것.
- 칸 간격(피치)은 대략 **115~120px**. 좌표 목록에서 같은 행의 x 값이 이 간격으로
  늘어서면 정상이고, 간격이 2배면 **가운데 칸이 검출 누락**된 것이다. 채워 넣어라.

## 3. 스프라이트를 칸에 배정

**카드·표지판류는 칸 중심보다 약 40px 위에 그려진다.** 그래서 `?` 좌표의 y 에 +40 을 더한 뒤
가장 가까운 칸에 배정한다. 파이프·`OUT` 글자는 칸 중심에 가깝다.

## 4. 포탈 분류 — 배수구 vs 다리

| 종류 | IN 쪽 겉모습 | 도착지 | 데이터 분류 |
|---|---|---|---|
| 배수구 | 색깔 있는 파이프 (`IN` 빨간 표시) | **같은 색 `OUT` 파이프 칸** | `portals` |
| 배수구 | 바닥의 마법진(빛나는 원반) | `OUT` 파이프 칸 | `portals` |
| 다리 | 밧줄 / 세로 장대 / 사다리 | **평범한 칸** (OUT 없음) | `bridges` |

- **화살표 방향은 무시하라.** 사다리 화살표가 아래를 향해도 `+15` 면 15칸 *전진*이다(map-20).
- **빨간 글씨 `-N`** (경고 삼각형 동반)만 실제 후퇴다(map-12 의 `-14`).
- `+N` 숫자는 지도에 인쇄되어 있고 OCR 이 거의 정확하다. 다만 빨간 `IN` 표시가
  숫자 하나를 가릴 수 있으니(예: `+19` 가 `+9` 로 보임) 검증식이 안 맞으면 이걸 의심하라.

## 4-1. 게임 규칙 (사용자 확정)

- **연쇄 워프는 없다.** 배수구를 타고 도착한 칸에 또 다른 IN 이 있어서 연달아 이동하는 일은
  일어나지 않는다. 도착 칸에는 반드시 `OUT` 파이프가 있다.
- 따라서 **어떤 배수구의 도착지가 다른 IN 파이프 칸으로 계산된다면 그 판독은 틀린 것이다.**
  경로를 다시 세거나, 인쇄된 숫자를 의심하라.

## 4-2. 인쇄된 숫자를 맹신하지 마라

`+N` 숫자는 지도에 인쇄된 값이지만 **오기가 있다.** 실제 사례:

- map-17 의 배수구 하나는 `+9` 로 인쇄돼 있으나 실제로는 **`+21`** 이었다.
  회색 IN 2개 / 회색 OUT 2개인데 OUT 둘은 경로상 3칸 간격, IN 둘은 9칸 간격이라
  둘 다 `+9` 인 것이 기하학적으로 불가능했다. 색 짝 + 검증식으로 `+21` 이 유일해였다.
- map-02 의 배수구 하나는 아예 `+N` 이 인쇄돼 있지 않아 색 짝과 검증식으로 `+16` 을 역산했다.

**우선순위: 검증식 > 색 짝 > 인쇄된 숫자.** 인쇄값과 검증식이 충돌하면 검증식을 믿고,
JSON 의 `"note"` 에 "지도에는 +X 로 인쇄돼 있으나 오기" 라고 남겨라.

## 4-3. 칸 수가 애매하면 연립방정식으로 풀어라

여러 지점에서 칸 수가 ±1 확정되지 않을 때, 눈으로 헤매지 말고 **미지수로 두고 식을 세워라.**
`(행마다의 칸 수)` 를 변수로 두면 배수구·다리 식들이 연립방정식이 되고, 보통 유일해가 나온다.
그 다음 해가 가리키는 지점만 확대해서 확인하면 된다.

실제로 map-12 는 이 방법으로 풀렸다 — 5개 식을 연립하니 "상단행 다음에 칸이 하나 더 있어야
한다"가 유일해였고, 그 지점을 4배 확대하니 `-14` 표지판이 **자기 칸을 갖고 있었다**
(상단행 칸에 매달린 장식으로 오인했던 것).

## 5. 검증식 — 반드시 통과시킬 것

```
배수구:  IN칸번호 + 이동칸수 == OUT칸번호,  그리고 그 자리에 실제로 OUT 파이프가 있어야 한다
다리  :  IN칸번호 + 이동칸수 == 그림상 다리가 닿는 칸
```

- 파이프는 **색이 짝**이다(갈색↔갈색, 파랑↔파랑, 회색↔회색). 검증식과 함께 이중 확인에 쓴다.
- **OUT 이 캐릭터·NPC 그림에 완전히 가려지는 경우가 있다**(map-05·09·18·21).
  다른 식이 전부 맞고 한 곳만 "그 자리에 OUT 이 안 보인다"면, 가려진 것으로 보고
  `"inferred"` 필드에 사유를 적어라.
- **식이 안 맞으면 칸 번호가 틀린 것이다.** 숫자를 억지로 맞추지 말고 경로를 다시 세라.
  ±1 이 안 맞으면 보통 (a) 세로 연결 기둥이 1칸인지 2칸인지, (b) 어떤 행의 끝 칸이
  실제로 있는지, (c) 계단식 꺾임에서 칸을 하나 빠뜨렸는지 중 하나다.

## 5-1. ? 카드는 색 마스크 말고 템플릿 매칭으로 세라

`find_qcards` 는 금색 '?' 글자의 색·크기 범위로 찾는다. 배경이 밝거나 카드가 캐릭터·NPC 에
살짝 가리면 그냥 놓친다 — 실제로 map-48·51 은 0개, map-33 은 4개 중 1개만 잡혔다.
**판독 당시 이걸 개수 대조에 썼다면 누락을 못 걸러낸다.**

대신 `scripts/adventure_qaudit.py` 는 카드 스프라이트 통째를 템플릿으로 놓고
정규화 상호상관(NCC)으로 훑는다. 카드는 게임 UI 에셋이라 지도마다 픽셀이 거의 같아서
상관계수가 0.78~0.95 로 뚜렷하게 뜬다. 56장 중 52장이 기록과 정확히 일치했고,
나머지 4장을 파보니 **3장이 진짜 누락**이었다(map-10 의 7번, map-15 의 3·36번, map-23 의 34번).

```bash
python scripts/adventure_qaudit.py          # 56장 전부
python scripts/adventure_qaudit.py 40 41    # 특정 지도만
```

- **NCC 가 기록보다 많으면 → 십중팔구 진짜 누락이다.** 해당 좌표를 칸에 배정해 확인하라.
- **NCC 가 기록보다 적으면 → 검출기 한계일 수 있다.** map-48 의 44번 칸 카드는 이미지
  최상단에 걸쳐 잘려 있어서(y<0) 템플릿이 들어갈 자리가 없었다. 기록이 맞았다.
- 새 지도를 판독했으면 이 감사를 **반드시** 돌려라. 개수가 맞아야 넘어간다.

## 5-1-1. 캐릭터가 카드 위에 서 있으면 어떤 검출기도 못 잡는다 (가장 중요)

**플레이어 캐릭터는 자기가 서 있는 칸의 ? 카드를 거의 완전히 덮는다.** 금색 테두리 왼쪽
일부만 삐져나오는 정도라, 색 마스크(`find_qcards`)도 상관계수(`adventure_qaudit.py`)도
전부 실패한다. 부분 매칭(inlier 비율)도 소용없었다 — 가려진 카드 점수 0.13 vs 배경 잡음
0.09 로 마진이 1.5배도 안 나와 자동 판정이 불가능하다.

**유일하게 통하는 방법은 이것이다:**

1. 캐릭터 스프라이트 자체를 템플릿 매칭해 **캐릭터가 밟고 선 칸**을 특정한다.
   캡처 세트에 캐릭터가 여러 명일 수 있다(실제로 4종이었다: 청발 40장 · 백발 7장 ·
   적발 2장 · 청록발 3장, 나머지 4장은 캐릭터 없음). 한 명 찾고 끝내지 말 것.
2. 그 칸만 **6~8배로 확대해 육안 확인**한다. 카드가 있으면 캐릭터 왼쪽 아래로
   둥근 사각형의 금색 테두리 호(弧)가 보인다.
3. 판단이 애매하면 **카드가 없는 게 확실한 칸과 나란히 붙여 비교**하라. 단독으로 보면
   타일 경계와 헷갈리지만, 나란히 놓으면 있고 없고가 즉시 갈린다.

이 절차로 56장을 훑어 map-19(5번 칸) · map-20(6번 칸) · map-40(3번 칸) 세 장을 찾았다.
셋 다 앞쪽 12칸 안이라 기본 화면에 그대로 영향을 준다.

> 처음 판독 때 이걸 놓쳤고, 사용자가 "캐릭터 뒤에 행운카드가 실제로 존재해" 라고
> 알려 줘서야 발견했다. **개수 대조가 맞아도 가려진 카드는 드러나지 않는다.**

NPC·몬스터 스프라이트도 원리상 같은 문제를 일으킬 수 있다. 다만 대부분 칸 사이 배경에
배치돼 있어 위험이 낮고, 이번 감사는 **플레이어 캐릭터 기준으로만** 전수 확인했다.

## 5-2. 인게임 '이동 가능 칸' 오버레이는 공짜 검증 자료다

일부 지도(map-48 등)에는 캐릭터 현재 칸 기준으로 `+2 +3 +4 …` 라벨이 붙은 노란 점선 칸이
찍혀 있다. 이건 행운카드 사거리 미리보기라서 **캐릭터 칸 + N == 라벨이 붙은 칸** 이 그대로
성립한다. map-48 은 이걸로 캐릭터가 선 2번 칸부터 4~14번 칸까지의 번호가 한 번에 확정됐다.
경로 방향이 헷갈릴 때 가장 값싼 확인 수단이니 라벨이 보이면 먼저 써라.

## 6. 출력 형식

담당 구간마다 **자기 파일**에 쓴다 (`scripts/adventure_maps_<시작>_<끝>.json`).
공용 파일을 건드리지 말 것 — 충돌 난다.

```json
{
  "26": {
    "squares": 35,
    "q": [4, 11, 16, 27, 30],
    "portals": [
      { "in": 3, "n": 26, "out": 29 },
      { "in": 23, "n": 10, "out": 33, "inferred": "OUT이 캐릭터에 가림 — 검증식으로 확정" }
    ],
    "bridges": [{ "in": 13, "n": 6, "out": 19 }],
    "items": [],
    "points": [],
    "next": 35
  }
}
```

- `squares` = 총 칸 수, `next` = NEXT 칸 번호(보통 `squares` 와 같다)
- `q` = ? 행운카드가 있는 칸 번호들 (오름차순)
- `items` / `points` 는 채우지 않아도 된다 (표시에 쓰지 않음)
- 검증식을 통과 못 시킨 지도는 **추측해서 넣지 말고** 결과 보고에 사유와 함께 남겨라.
  틀린 데이터보다 빈칸이 낫다.
