## 3. README 와 실제 코드의 차이 — 우리는 **코드**를 따른다

| 항목 | README | 실제 코드 (v9.17) |
|---|---|---|
| 방어 뒤 덧셈 순서 | `f32(B1 + FD + ADD)` → `f32(− F)` | `f32(B1 + FD)` → `f32(− F)` → **`f32(+ ADD)`** (단계마다 f32) |
| 관통 잔여율 | `(100 − PEN)/100` | **`f32((100 − PEN)/100)`** |
| 지배력 계수 | `f32(1 + f32(Dom/100))` | **`f32(f32(100 + Dom)/100)`** |
| 소환 공격항 | `(W+1) × (SC+100) / 50` | **`(W+1) × ((SC+100)/50)`** (나누기 먼저) |
| 방어 초과 시 | `R_min ∈ {1, 2}` | 최소 1, 최대 **max(2, T)** 로 범위 출력 |
| 소환 공식 | 상수 `+1, 95/105, 50, 20` 고정 | **소환체 프로필 × 소환 몹 기본값** (§5) |

덧셈 순서는 수학적으로 같지만 f32 반올림 위치가 달라 결과가 달라진다.
무작위 입력 2만 건에서 **41%가 README 식과 값이 달랐고**, 최대 차이는 0.16%다.
실측과 정수 단위로 맞추려면 코드 쪽 순서가 필수다.

## 4. 최종 공식 (직타)

```
MIN = floor(rawMIN × (100 + FMIN) / 100)          FMIN = 최종 최소 대미지 %
MAX = floor(rawMAX × (100 + FMAX) / 100)
CD  = floor(rawCD  × (100 + FCD)  / 100)
주스탯_eff = floor(STR × (1 + EFF/100))            EFF = 근력/마법력 효율 (직타만)

B0 = 주스탯_eff + floor(W × (C + 100) / 50)        W = 무기공격력 난수(물리) / 속성력(마법)
a  = 물리 30L+200 / 마법 20L+200
m  = f32(1 − DEF/(DEF + a) × f32((100 − PEN)/100))
B1 = f32(f32(B0) × m)
B2 = f32(B1 + FD)
B3 = f32(B2 − F)                                   F = 대상 피해 감소 (고정값)
U  = f32(B3 + ADD)                                 ADD = 일반/보스 추가 대미지
K  = 100 + (크리 ? floor(CD × (1000 − ELASTICITY)/1000) : 0) + 백어택 + 근거리 + 상태이상
T  = floor(f32(f32(U × f32(K/100)) × Q) / 100)     Q = MIN ~ MAX 난수
D  = T > 0 ? T : 1~2
g  = f32(f32(100 + Dom)/100)
대미지 = floor(D × (100 − Guard)/100 × g)
```

- 난수는 **물리 직타만 둘**(W, Q), 마법 직타·소환은 Q 하나. 결과는 범위다.
- 평균은 난수 구간을 중점 적분한다 — 물리 직타 256×256 격자, 그 외 16,384점. 중앙값 한 점과는 0.01% 안쪽 차이.
- 조건부(백어택·근거리·상태이상)는 크리 저항을 받지 않는다.

구현: `src/utils/damageFormula.js`

## 5. 소환 공식 — 소환체 프로필 × 소환 몹

```
statTerm = floor(STR × 소환체.Atk/100) + 몹.Base_Atk              (EFF 미적용)
attack   = W × 소환체.Weapon_Dam/100 + 몹.BASE_NORMAL
B0       = statTerm + attack × ((SC + 100)/50)
m_s      = 관통을 표시값과 무관하게 99% 로 계산한 m
FD_s     = floor(FD × 소환체.Damage_Absolute/100) + 몹.BASE_DAMAGE_ABSOLUTE
ADD_s    = floor(ADD × 소환체.Boss_Dam(또는 Mob_Dam)/100)
Q        = floor(MIN × 소환체.All_Mix_Dam/100) + 몹.Base_Atk_Min_Dam
         ~ floor(MAX × 소환체.All_Mix_Dam/100) + 몹.Base_Atk_Max_Dam
cd       = floor((rawCD − 50) × 소환체.Cri_Dam/100) + 몹.BASE_CRITICAL_DAMAGE
크리 K   = floor(floor(cd × (100 + FCD)/100) × (1000 − ELASTICITY)/1000)
백어택   = 몹.BASE_BACK_DAM (캐릭터 백어택 아님), 근거리·상태이상 미적용
```

**README 의 고정 상수는 "기본 몹" 값이다.**

| 데이터 | 기본값 | 기본값과 같은 비율 |
|---|---|---|
| 몹 `(Base_Atk, BASE_NORMAL, 최소, 최대, 크댐, 백어택, 고정)` | `(1, 1, 95, 105, 50, 20, 0)` | **515 / 523** |
| 소환체 `Atk = All_Mix_Dam = Cri_Dam` (= S) | — | **332 / 336** |
| 소환체 `Weapon_Dam`, `Damage_Absolute` | 100 | 336 / 336 |
| 소환체 `Boss_Dam`, `Mob_Dam` | 100 | 335 / 336 |

예외 4종은 `Cri_Dam = 100` 인데 `Atk` 이 70~95 인 경우다. 우리 엔진은 `skill.profile`·`skill.mob` 으로 예외를 받는다.

## 7. 스탯 누적 규칙 — 우리 `equipDelta` 와 구조는 같고 반올림이 다르다

원본 `scaled(표시값, 누적%, 가산, 추가%)`:

```
기본값   = ceil(표시값 × 100 / (100 + 누적%) − 1e-8)      ← 표시값에서 역산 (올림)
새 표시값 = floor((기본값 + 가산) × (100 + 누적% + 추가%) / 100)   ← 내림
```

우리 `src/utils/battlePower.js` 의 `applyEquipDelta` 는 같은 구조를 **실수 그대로** 계산한다
(`새 기본 × (1 + 새 누적%)`, 반올림 없음). 전투력 환산에서는 차이가 무시할 만하지만,
대미지를 정수 단위로 맞추려면 이 올림·내림을 따라야 한다. → §9-3

### 9-1. 실측 검증 (가장 먼저)

**목각인형 프리링**은 방어·피해감소·Guard·크리저항이 전부 0이라 기준점으로 쓴다.

필요한 데이터(한 건당): T창 스탯 전체, 캐릭터 레벨, 스킬 이름·레벨·계수, 대상, 대미지 **20~30회**의 크리/비크리별 최솟값·최댓값.

순서: 목각인형 비크리 → 목각인형 크리 → 보스형 강철인형(방어 437만 · Guard 90 · 크리저항 700).
보스형 강철인형에서 대상 수치를 역산할 때:
- **크리저항** — 같은 대상에서 크리/비크리 배율 하나로 결정된다 (예시 스탯 기준 저항 0 → 119배, 700 → 36.5배).
- **Guard** — 고정 대미지처럼 더해지는 스탯을 알려진 만큼 바꿔 증가분을 보면 결정된다.
- **피해감소 F** — Guard 를 안 뒤 남은 식에서 결정된다.
- **방어력** — 관통 99%면 대미지에 영향이 사실상 0이라 역산할 수 없고, 할 필요도 없다.

맞으면 그 케이스를 테스트에 "실측" 블록으로 추가하고 프리셋을 `verified: true` 로 바꾼다.

### 9-2. `SKILL_DATA` 를 가져올지 — **사용자 결정 필요**

가져오면 직업·스킬·레벨만 고르면 계수와 소환체 프로필이 자동으로 채워진다. 다만
- 게임 클라이언트에서 추출한 데이터로 보이고, 라테일은 액토즈소프트 IP 다
  (이 앱은 이미 확률표 탭을 저작권 문제로 특정 계정에만 노출하고 있다).
- 3MB 라 번들에 넣으면 대미지 탭 청크가 커진다 (지연 로딩이라 첫 화면엔 영향 없음).

### 9-3. 우리 스탯 누적 반올림을 `scaled()` 에 맞출지

§7. 전투력 식은 이미 실측으로 회귀·보정돼 있어 건드리면 기존 수치가 흔들릴 수 있다.
대미지 탭에서만 `scaled()` 규칙을 쓰는 쪽이 안전하다.

### 9-4. 환산을 대미지 기준으로

§8. 스펙업 방향 분석의 "최종 크리티컬 대미지는 크리 확률 100% 가정" 같은 근사를 없앨 수 있다.

## 10. 이어받는 세션에게

- 엔진은 순수 함수라 `node -e` 로 바로 돌려볼 수 있다.
- 값이 안 맞을 때 의심 순서: ① f32/floor 위치(§3) → ② T창 표시값 vs raw 해석 → ③ 스킬 계수 → ④ 대상 수치
- 원본과 다시 대조하려면 저장소 `index.html` 의 첫 번째 `<script>` 에서
  `calculateChannel` 과 그 의존 함수(`attackPipeline`, `hitFlow`, `hitRange`, `finalDamageFlow`,
  `averageDamageEstimate`, `kahanAdd`, `estimateChannelAverages`)를 떼어 `node:vm` 에서 실행하면 된다.
  `f32 = Math.fround`, `floor = Math.floor`, 표본 상수 `16384 / 256 / 16384` 를 함께 정의한다.
- 원본이 갱신됐는지는 `gh api repos/alfm201/damage-test/commits` 로 확인한다 (익명 API 는 요청 제한이 걸린다).
- 프로젝트 규칙: 브랜치 없이 `main` 에 바로 커밋·푸시. UI 세부는 묻지 말고 기존 톤(한 줄 설명 + 접기, cyan 단일 포인트)에 맞춘다.
